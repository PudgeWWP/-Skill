# 立项确认与文档规范

## 必需内容

先汇总全案供用户确认。模块可合并或分章，但须覆盖以下11项：

| 内容 | 要求 |
|---|---|
| 1 游戏名字 | 根据题材与玩法直接拟定一个名字，列入确认稿，用户可修改 |
| 2 玩法概括＋立项案 | 简洁副标题，末尾包含“立项案”三个字 |
| 3 核心玩法概括 | 用字母 x 连接实际包含的核心玩法，不强凑数量 |
| 4 一句话概括 | 讲清题材、美术、主要玩法及循环 |
| 5 美术展示 | 嵌入已选模拟实机图，等比例配功能图注；未生图按用户选择处理 |
| 6 立项基础逻辑 | 为什么选择玩法，满足什么需求，系统如何支持，覆盖目标用户 |
| 7 市场角度分析 | 用玩法接近的真实产品比较体验与竞争，优先用户提供的参考 |
| 8 原型拆解 | 逐款说明参考产品的借鉴亮点、范围、如何改编到本项目 |
| 9 差异化阐述 | 必须用表格：维度、参考方向或产品、本项目方案、体验价值 |
| 10 落地结合 | 玩法题材美术如何结合，混合玩法的连接过渡和阶段节奏 |
| 11 产品总结 | 核心优势、可能风险、应对思路或验证方向 |

按产品或要求可增加循环图、验证范围、制作计划等。不能编造预算、工期、团队、定价或内容量。待定事项集中放在总结，不用零散备注。

## 市场分析

- 实际调研，优先官方说明与实机；观察事实和分析判断分开，评论量不等于销量，多类受众不能直接相加。
- 优先使用用户提到且玩法接近的产品，补充相邻产品时说明理由，不能以知名度替代相关性。
- 全文统一产品中文叫法。没有稳定中文名时说明并用原名，不编造翻译。
- 聚焦相近玩法吸引力、本项目切入点与取舍。避免无依据的市场空白、必然成功和用户叠加断言。
- 内部工作记录保留来源日期以便核对；**最终文档默认不出现引用编号、来源链接、调查／调研来源列表或附录。** 用户另行要求时再提供。

## 排版

- **开篇居中：游戏名、玩法副标题、平台／题材概括（如有）、核心玩法概括。** 正文章节及小标题默认统一左对齐。
- 中英文统一字体，默认可选实际安装的微软雅黑／Microsoft YaHei。标题和表头按层级统一加粗，正文常规字重，不混用衬线、无衬线、伪斜体和不同中英文字重。
- 参考用户方向设置字号、标题色、行距、段距与少量重点底纹。可从项目名28—30pt、一级18—20pt、二级14—16pt、正文11pt、表格10.5—11pt起步，按内容调整，不固定页数。
- 章节先说关键判断再展开。利用字号、颜色与空白建立层级，避免密集加粗和大块装饰框。
- 不自动加版本号、制作日期、生成说明、历史来源说明等小备注；待定内容用正常字号集中表达。
- 图片保持比例与识别大小；表格有合适列宽、留白、重复表头及自然行高，避免截字、挤压和不合适跨页。页码可保留。

## 字体一致性

仅设 `font.name` 可能仍被主题覆盖。需锁定 `w:rFonts` 的 ascii、hAnsi、eastAsia、cs，清理 Theme 属性；检查 styles.xml、stylesWithEffects.xml、正文和页眉页脚，保持 b／bCs 与字号规则一致。

可使用 [字体规范化工具](../scripts/normalize_docx_fonts.py)，在文档层级与字重设置完成后统一字体，不能替代视觉检查：

```text
python scripts/normalize_docx_fonts.py input.docx output.docx --font "Microsoft YaHei"
python scripts/normalize_docx_fonts.py output.docx --check --font "Microsoft YaHei"
```

用 documents 技能解析出的运行环境执行。默认另存，输出应是新的文件；更新原件须检查后再替换。

## 交付检查

结合 documents 技能，生成后渲染并查看全部页面。核对居中、字体字重、图片清晰、表格换行、留白、无孤立标题和单行备注页。

默认转换器不可用时先诊断。Windows 如有可用 Word，可只读打开当前文档工作副本导出 PDF，再用可用工具渲染检查；只关闭自行创建的文档和应用实例，不操作用户其他文档。额外权限按环境规则处理，不隐瞒转换失败。

只交付要求的最终 Word，预览 PDF／PNG与研究过程留工作区。交付说明不要重新附上被要求删除的来源列表与备注。
